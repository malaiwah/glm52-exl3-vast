tree `a5aa59cc`, and FlashInfer `801d57a`.

The selected production geometry remains TP4/DCP4, native rank-sliced TR3
MTP-5, a 2,048-token prefill batch, C8 graphs through row 48, exactly 2,048
GPU KV blocks / 524,288 logical tokens, 125 GiB aggregate LMCache DRAM, and a
512 GiB bounded local-NVMe tier. `VLLM_EXL3_TRELLIS_MIN_M` is intentionally
absent: r13 declares 1 as the backend capability for both target and draft.
The turnkey mixed-K adapter inherits that declaration and uses a new compile
cache namespace.

The r13 batch/depth challenge produced a clear safety boundary:

| candidate | first-request result | verdict |
|---|---|---|
| MTP5 / batch 3,072 / graph 48 | 36 MiB mixed-K output-conversion OOM | reject |
| MTP3 / batch 3,072 / graph 32 | same 36 MiB first-request OOM | reject |
| MTP5 / batch 2,048 / graph 48 | 32K, 128K, C1 and C8 completed without OOM | select |

MTP3 therefore did not buy enough request-time workspace to recover the larger
prefill plan. At the safe 2,048-token shape, r13's published MTP3 control is
101.92 tok/s; it provides no evidence that depth 3 is better than the final
MTP5 result below. The selected MTP5/2,048 shape is the explicit accepted
fallback, not an accidental unchanged default.

The first isolated r13 control measured 2,249.1/2,100.8 tok/s at 32K/128K,
87.5 tok/s at C1 with mean acceptance length 4.69, and 285.5 aggregate tok/s
at C8 with mean acceptance length 5.15. The final image was then measured on
the live production endpoint:

| final r13-v2 gate | result |
|---|---:|
| 32K / 128K unique-prefix PP | 2,197.1 / 2,062.8 tok/s |
| C1 aggregate TG / MTP5 MAL | 108.8 tok/s / 4.96 |
| C2 aggregate TG / MTP5 MAL | 173.0 tok/s / 4.81 |
| C4 aggregate TG / MTP5 MAL | 255.0 tok/s / 5.32 |
| C8 aggregate TG / MTP5 MAL | 332.9 tok/s / 5.41 |
| request failures / preemptions | 0 / 0 |

User agent traffic shared the endpoint throughout that final run, so these are
production measurements rather than isolated laboratory numbers. The C1
stretch goal cleared despite that traffic; cold PP remained below 2,400
tok/s. Exact context, correctness and runtime safety take precedence for this
higher-fidelity option.

The final API gate passed ordinary and thinking chat, streaming usage,
preserved-thinking multi-turn, strict structured JSON with and without
thinking, and tool choice/call/result round trips. A single exact
522,360-token prompt placed five needles at 1%, 10%, 50%, 90% and 99%:
all five were returned exactly in 311.061 seconds, the degeneration detector
remained clear, and ordinary queued traffic resumed without an OOM.

This run also closes
[local-inference-lab/vLLM issue #183](https://github.com/local-inference-lab/vllm/issues/183).
With `VLLM_EXL3_TRELLIS_MIN_M` absent, both target and native rank-sliced
draft planned a `[1, 48]` window, compiled and captured. No eager-parity path
was entered.

The tables below are the earlier r11 offload-isolation evidence that established
the same 2,048-token safety boundary and tier sizing.

## Hardware and selected geometry

- 4x NVIDIA RTX PRO 6000 Blackwell, 96 GB each, 280 W power limit
- NVIDIA driver 595.71.05, CUDA 13.2
- TP4/DCP4, dynamic-token NVFP4 MLA KV, native TR3 MTP-5
- `GPU_BLOCKS_OVERRIDE=2048`: `2,048 × 64 × DCP4 = 524,288` active tokens
- `MAX_MODEL_LEN=524288`, `MAX_NUM_BATCHED_TOKENS=2048`
- `SPARKINFER_INDEXER_TWO_LEVEL_FOLD_MAX_MIB=64`
- `OFFLOAD_FRACTION=0.5`: 125 GiB aggregate DRAM on the 251 GiB host
- optional `PREFIX_CACHE_DISK_GB=512` on `/mnt/fast` RAID0 NVMe

The earlier 3,072-token/256 MiB-fold shape booted but OOMed its first 128K
request on a 36 MiB mixed-K output conversion. Reducing active GPU KV was not
necessary: bounding the two transient workspaces made the complete 524,288
pool usable.

## Results

| Gate | Native DRAM | LMCache DRAM | LMCache DRAM + NVMe |
|---|---:|---:|---:|
| active GPU KV | 524,288 | 524,288 | 524,288 |
| idle free VRAM/GPU | 3,466 MiB | 2,633–2,637 MiB | 2,637 MiB |
| 128K cold PP | 2,158 tok/s | 2,100 tok/s | 2,143 tok/s |
| 128K decode sample TPOT | 17.13 ms | 9.97 ms | 9.91 ms |
| 128K decode sample MAL | 2.50 | 4.15 | 4.23 |
| 65,024-token DRAM reload | 0.568 s | 0.508 s | not repeated |
| 131,076-token restart restore | n/a | n/a | 1.254 s |

The isolated MAL rows are single stochastic outputs and are not a
connector-quality comparison. PP is within normal run variance; neither
LMCache nor its filesystem tier produced a repeatable PP/TG regression.

The native reload moved 2.079 GB in 0.402 s. The LMCache NVMe restart restore
reported 6.51 GB/s from filesystem L2 to DRAM and 14.7–17.1 GB/s from DRAM to
GPU across ranks. The identical prompt took about 61 s to recompute before it
was cached.

Near-maximum cold gates with both LMCache tiers enabled:

| prompt | duration | PP | peak reported GPU-KV |
|---:|---:|---:|---:|
| 520,001 tokens | 297.2 s | 1,749.6 tok/s | 96.9% |
| 524,012 tokens | 304.4 s | 1,721.4 tok/s | 99.3% |

Both completed without an OOM. The 524,012 prompt plus one output token is the
practical request ceiling; the remaining 275 tokens under the 524,288 hard
limit are API/chat-template safety margin.

## Storage and release boundaries

LMCache filesystem L2 is write-through. It did not preallocate the 512 GiB
limit or change idle VRAM. The directory grew to 39 GiB during the boundary
matrix. AIBeast had 748 GiB free before the test, so a 512 GiB limit still
needs an operator capacity check and operational free-space margin.

Native vLLM filesystem offload was not presented as a production comparison:
[local-inference-lab/vLLM PR #165](https://github.com/local-inference-lab/vllm/pull/165)
is still open, and GG v20-r11 does not contain its `max_cache_size_bytes`/LRU
implementation. The appliance therefore rejects native+disk rather than
offering an unbounded tier that can fill the device.

GG v20-r12 and r13 were published after the original offload-isolation run.
The final qualification uses r13. Its corrected matched MTP0 comparison is
44.66 tok/s on stock r11 versus 48.61 on r13 (`+8.85%`); no separate MTP3
speedup is claimed because acceptance and run variance dominate that
comparison. Open [vLLM PR #190](https://github.com/local-inference-lab/vllm/pull/190)
and [SparkInfer PR #92](https://github.com/local-inference-lab/sparkinfer/pull/92)
remain moving upstream work, so the appliance pins their reviewed r13 result
trees rather than their branch heads.

Raw logs, container inspections, metrics snapshots, and benchmark JSON remain
on AIBeast under `/mnt/fast/build/r12-kv-sweep-20260730/` and
`/mnt/fast/build/r13-production-qualification-20260730/`.
