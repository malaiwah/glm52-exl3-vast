# GG v20-r31 / GLM-5.2 3.42-bpw qualification

This is the production-shape qualification for the turnkey r31 derivative on
AIBeast. It combines immutable GG v20-r31 with the appliance's reviewed vLLM
#258/#270/#271 runtime overlay and the r31-native B12X route prewarm.

## Exact serving contract

| item | qualified value |
|---|---|
| checkpoint | `willfalco/GLM-5.2-EXL3-TR3-3.42bpw@a350292cb2038f2c31732569a711a89e5d72fd46` |
| topology | TP4 / DCP4 / native MTP3, probabilistic proposals |
| weights | EXL3 shared-H 3.42 bpw plus online Trellis K6 |
| KV | dynamic-token NVFP4 MLA with FP8 RoPE, 368-byte record |
| request / logical GPU KV | 520,192 / 520,192 tokens |
| KV allocation | `KV_CACHE_MEMORY_BYTES=4518907904` per rank; no block override |
| scheduler | C12, 3,072 batched/prefill rows |
| capture | graph sizes 4..48, graph/trellis maximum 48 |
| prefix offload | LMCache 125 GiB aggregate DRAM plus bounded 512 GiB NVMe |

The byte pool comes from the observed per-rank LMCache record geometry:
`4,447,744 bytes / 512 tokens = 8,687 bytes/token`; therefore
`520,192 * 8,687 = 4,518,907,904` bytes. This retains a standard maximum
request without using vLLM's testing-only block-count override, which would
bypass the profiled available-memory budget.

## Memory gates

The initial C12 server exposed exactly 520,192 logical tokens. CUDA graph
capture used 0.74 GiB/rank and left about 3.24 GiB physically free after
startup. Four concurrent 16K prompts with `prompt_logprobs=20` returned the
exact row counts with no failure. After first-use/JIT allocations the server
retained about 1.00--1.10 GiB/rank; after cold 64K/128K prefill the minimum
observed free memory was 0.84 GiB. There were no worker restarts, preemptions,
or OOMs in this arm.

Two tempting alternatives were rejected:

- GMU-0.95 automatic sizing exposed 643,840 logical tokens but eventually
  left only about 41 MiB free. A real 71K-prompt agent request then OOMed on a
  48 MiB EXL3 activation. Startup's suggested automatic KV byte values do not
  account for every late K6/sparse-prefill allocation in this stack.
- C8 with a 4,096-row scheduler/EXL3 arena exposed the intended 520,192-token
  pool but used 0.56 GiB for graphs and started with only 2.47 GiB free. Its
  first four-stream 16K prompt-logprobs replay OOMed all ranks on the same
  48 MiB activation with only 8--35 MiB free. The 4,096-row PP arm is not a
  production-safe trade at this context size.

## Performance gates

Uncached single-request prefill:

| prompt | throughput |
|---:|---:|
| 65,528 tokens | 2,323.9 tok/s |
| 131,073 tokens | 2,199.5 tok/s |

Matched 1,024-input / 512-output decode, 24 requests per level, temperature
1.0 and seed 42:

| concurrency | aggregate output | mean TPOT | MTP MAL | failures / preemptions |
|---:|---:|---:|---:|---:|
| C1 | 108.7 tok/s | 8.44 ms | 3.609 | 0 / 0 |
| C4 | 226.5 tok/s | 16.06 ms | 3.575 | 0 / 0 |
| C12 | 266.8 tok/s | 33.32 ms | 3.408 | 0 / 0 |

The C8 sample was contaminated by unrelated agent traffic and is not used as
a headline result. C12 is the selected knee: it increases aggregate capacity
while retaining the memory margin that C16's wider graph pool would consume.
It is a scheduler envelope for small concurrent requests, not twelve complete
520K sessions resident at once; vLLM can preempt and LMCache can reuse prefixes.
