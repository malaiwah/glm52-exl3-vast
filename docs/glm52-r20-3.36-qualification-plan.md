# GLM-5.2 r20 / 3.36-bpw qualification plan

Prepared 2026-08-02 and refreshed for r20 for the next explicit AIBeast
maintenance window. This plan does not authorize changing the currently
healthy production service.

## Objective and candidate

Qualify the higher-accuracy
[`willfalco/GLM-5.2-EXL3-TR3-3.36bpw`](https://huggingface.co/willfalco/GLM-5.2-EXL3-TR3-3.36bpw)
checkpoint on the current Gilded Gnosis r20 integration, then select the best
production balance across native dense weights, online dense MXFP8, cached
online Trellis K6, MTP depth, GPU ordering, and concurrency. Preserve the
existing requirements: 524,288 maximum model length,
at least eight small concurrent requests, approximately 2,400 tok/s long
prefill where the 280 W limit permits it, at least 100 tok/s C1 generation,
no OOM or degeneration, five-depth maximum-context retrieval, and working
LMCache DRAM/NVMe reuse.

## Executed result — promoted profile

The 2026-08-03 AIBeast window qualified and selected the following exact
shape on four 96 GiB RTX PRO 6000 Blackwell cards, driver `595.71.05`, CUDA
13.2, capped at 280 W/GPU:

```text

image       r20 plus SparkInfer mixed-tier cache-key ABI-5 repair (#114)
TP/DCP      4 / 4

KV          dynamic-token NVFP4 MLA + FP8 RoPE, 2,048 blocks / 524,288 tokens
speculation native MTP3, probabilistic proposals

graphs      32; mixed-prefill block 32
offload     LMCache 125 GiB DRAM + bounded 512 GiB local NVMe
GPU order   physical 2,1,0,3 (logical rank 0 on the coldest card)
```

The warm matched gate measured 2,285.8 / 2,175.6 / 2,060.1 tok/s prefill at
3K/32K/128K. Aggregate decode was 119.8 / 169.0 / 295.1 / 342.3 tok/s at
C1/C2/C4/C8; mean acceptance length was 3.73 / 3.33 / 3.75 / 3.48. There were
no request errors or preemptions. The first inference pass was retained
separately because first-use JIT warnings made its C1 result a cold-start
number, not a steady-state result.

The release request contained 521,276 actual prompt tokens and five needles
at 1/25/50/75/99% depth. It retrieved 5/5 exactly, reported no degeneration,
peaked at 96.7% GPU-KV use, and completed without OOM. The strict-JSON-with-
thinking gate and both served aliases (`GLM-5.2`, `local-primary`) passed.

LMCache was not accepted from configuration alone. After 17 unique 32K
documents displaced a target prefix from GPU, the repeat recorded zero GPU
hit tokens and 32,768 external hit tokens. TTFT fell from 14.676 seconds
cold to 0.171 seconds from DRAM. The filesystem tier completed 12,800 chunks
and held 52.4 GB during that gate without allocation/store failures. A
deterministic 131K prefix was retained for the final port-8000 restart and
cross-restart NVMe-read proof.

Automatic KV sizing is explicitly rejected for this production posture. It
exposed 741,888 tokens but left only about 43 MiB free; the first 32K prefill
needed a 48 MiB mixed-K temporary and OOMed. Pinning 2,048 DCP4 blocks keeps
the complete binary-512K request envelope while leaving about 1 GiB/rank
under sustained load. This failure is now a configurator warning.

The precision matrix selected K6: dynamic-NVFP4/RoPE8 mean KLD was
`0.08250703559901781`, identical in two runs. For context, r20 native 3.36
measured `0.0810645975420023`, conservative MXFP8 measured
`0.08123787365850146`, and the repeated r17 3.25 control measured
`0.09496129061216893`. K6 used 78.83 GiB/GPU at MTP0, versus 80.06 GiB for
MXFP8 and 83.43 GiB native. MXFP8 later failed a C4 production-shape request
with a cuBLAS internal error at only 4–24 MiB free and was rejected.

MTP3 was selected over MTP5. MTP5 could win individual C1 samples, but MTP3
retained 36,352 more KV tokens in the unconstrained comparison and produced
the stronger repeatable C8 aggregate result. C16 completed but fell below C8
aggregate throughput and raised TTFT to 12.36 seconds, so the production
scheduler remains eight active sequences; additional requests queue/preempt.

## Why r20 changes the experiment

r20 is a strict r19 superset, but it is not merely a newer container tag. Its
[launch contract](https://github.com/local-inference-lab/rtx6kpro/blob/master/models/glm5.2_v20.md)
consolidates [vLLM #228](https://github.com/local-inference-lab/vllm/pull/228)
with [SparkInfer #112](https://github.com/local-inference-lab/sparkinfer/pull/112)
and [#113](https://github.com/local-inference-lab/sparkinfer/pull/113), and
introduces three directly relevant changes:

1. qualified block-32 mixed K3/K4 prefill, with the slower experimental TMA
   producer-warp path explicitly excluded;
2. the appliance-originated `VLLM_EXL3_PREFILL_CAPACITY` policy in the
   consolidated runtime: blank/unset remains the fastest default, while
   `1024` is the capacity-first candidate expected to trade roughly 7-12%
   prefill throughput for persistent-arena memory;
3. `ONLINE_QUANT=exl3-b6`, which encodes eligible aligned BF16 dense matrices
   as native Trellis K6, leaves serialized K3/K4 routed experts unchanged, and
   uses the preset's MXFP8 fallback for ineligible dense shapes.

The working quality/memory hypothesis is stronger than “K6 sits between BF16
and FP8”: online K6 is expected to use less dense-weight VRAM than FP8/MXFP8
while also producing lower BF16-relative KLD. Trellis encoding can spend its
six bits more effectively than a generic scalar floating-point overlay, so
nominal bit width alone does not predict divergence. This is still a release
hypothesis until the same tensors, KV precision, reference logits, and KLD
positions are compared on AIBeast. Keep **online weight FP8/MXFP8** distinct
from **FP8 KV cache** in every artifact and table.

The K6 cache is content-addressed by checkpoint/source/encoder/rank/geometry
identity and stored as atomic per-rank safetensors under
`/cache/exl3-online`. Normal serving uses `readwrite`; `readonly` and `off` are
diagnostic modes. The published r20 gate used 3.25 bpw, TP4/DCP1/MTP0, 131K
and one sequence. It created 1,644 files (11,897,961,792 bytes), reduced cold
empty-cache startup from a conversion-heavy 827.04 seconds to 113.94 seconds
on a warm restart, and reported 53.08-53.23 tok/s C1 with 3,635.67/3,512.62
tok/s 8K/64K prefill. Those results establish the implementation, not our
3.36-bpw, DCP4, MTP3/5, C8/C16, 524K, dynamic-NVFP4 KLD, or LMCache posture.

### r20 mixed-tier cache-key field repair

The first 3.36-bpw GPU boot exposed a release blocker that the fixed-split
3.25-bpw checkpoint cannot reproduce. SparkInfer PR #112 made the child K3/K4
kernels dynamically size their expert dimension, so their child cache keys
intentionally omit `num_experts`. The outer mixed dispatcher still compiles
tier-local expert bounds, but its ABI-4 key also omitted those counts. Layer
3's `206/50` split and layers 4-77's `160/96` split therefore collided and the
later layout reused a stale launch, producing a CUDA illegal-address failure.

The appliance applies the minimal ABI-5 repair from
[SparkInfer #114](https://github.com/local-inference-lab/sparkinfer/pull/114):
both tier counts are part of the outer key. The patch fails closed on an
unexpected source tree and its checksum is pinned in the image build. On
AIBeast, the repaired native one-grid path independently planned both layouts
under `CUDA_LAUNCH_BLOCKING=1` and completed all 2,047 KLD positions without a
CUDA fault; mean dynamic-NVFP4/RoPE8 KLD was `0.0810645975420023`. Do not use
the diagnostic serial fallback for qualification or production.

Use a new persistent cache namespace keyed to r20, the 3.36 checkpoint
revision, and the ordered AIBeast GPU mapping. Capture the cold cache creation
count/bytes/manifest hash and then require a warm restart with the same entry
count, zero encodes, identical manifest hash, and no corruption or stale-cache
warning. Do not delete or reuse another model's cache to manufacture the test.

This is encouraging capacity evidence, not a matched appliance qualification:

record the missing fields in our matched run.

For every LMCache-enabled r20 candidate, require:

```text
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False
```

This is a compatibility setting, not a PP/TG tuning candidate. The maintained
v20 wrapper disables expandable segments because LMCache registers GPU KV
storage by virtual address. Stable-address CUDA IPC is also important to the
custom SparkInfer/B12X PCIe collective. Preserve any other allocator options,
record the fully resolved value, and require the startup log to explain the
override. The current r17 service's successful use of `expandable_segments:True`
is useful soak history but does not supersede the newer wrapper contract.

Because fixed segments can expose fragmentation that a successful cold boot
does not reveal, add an allocator soak: alternate short and near-maximum unique
requests, force LMCache L1/L2 insertion and eviction, run C8 bursts, and then
repeat a maximum-context request without restarting. Capture reserved versus
allocated CUDA memory, free VRAM, cache usage, preemptions, OOMs, and output
correctness. A no-LMCache `expandable_segments:True` boot may be retained as a
diagnostic control, but do not promote an LMCache service with it enabled.

## Why MTP3 and MTP5 both need qualification

GLM-5.2 stores one MTP layer. `MTP=3` and `MTP=5` recursively use that layer to
propose three or five tokens; they do not select different checkpoint heads.
The deeper draft wins only when its fourth and fifth positions are accepted
often enough to repay their draft and verification work.

Existing evidence conflicts in a useful way:

- a matched six-prompt field workload favored MTP3: 84.10% draft acceptance,
  mean acceptance length 3.523, and mean/p95 TPOT 16.962/23.647 ms, versus
  39.84%, 2.992, and 25.104/48.709 ms for MTP5;
- the current AIBeast coding-agent workload has repeatedly shown MTP5 mean
  acceptance lengths above 5, with healthy C1 generation above 100 tok/s.

Run both depths against the same retained request corpus, seeds, temperature,
quantization, KV mode, GPU order, and cache posture. Give reasoning responses
ample output budget; short-answer microbenchmarks alone are not representative.

### Matched MTP gate at eight sequences

| setting | MTP3 | MTP5 |
|---|---:|---:|
| `MAX_NUM_SEQS` | 8 | 8 |
| required query window | `8 * (1 + 3) = 32` | `8 * (1 + 5) = 48` |
| graph/Trellis minimum | 32 | 48 |
| draft sampling | test the current production probabilistic mode first; add a matched greedy pair only if it remains a candidate |

Record C1/C2/C4/C8 TG, TPOT p50/p95, TTFT, MAL, per-position acceptance,
accepted/drafted throughput, active KV, idle/peak VRAM, preemptions, power, and
answer correctness. Select MTP3 unless MTP5 produces a repeatable service-level
win on the retained agent corpus rather than only a higher best-case MAL.

## Sixteen-request concurrency gate

`MAX_NUM_SEQS=16` is a scheduler ceiling, not a promise of sixteen 32K or 512K
sessions. The 524,288-token GPU KV pool is shared: sixteen 32K prompts consume
the complete pool before output and block overhead, so vLLM must queue or
preempt larger combinations.

Test C1/C2/C4/C8/C12/C16 with:

1. zero/short-context decode for the saturation curve;
2. unique 8K prompts to avoid prefix-cache inflation;
3. a coding-agent corpus with realistic prompt/output distributions;
4. one bounded mixed-context load that deliberately exercises scheduler
   waiting and recoverable preemption without exceeding the configured pool.

MTP3 at C16 requires a 64-query graph/Trellis window. MTP5 at C16 requires 96.
Do not advertise C16 while leaving `VLLM_EXL3_TRELLIS_MAX_M` or graph capture
below the corresponding query width. Qualify MTP3/C16 first. Attempt MTP5/C16
only if r20 validates and captures the 96-row plan with adequate headroom; a
fallback outside the captured Trellis path is not a production qualification.

Report aggregate TG, per-request TG, p50/p95 TPOT and TTFT, MAL, scheduler
waiting, preemption/recompute counts, errors, peak active KV, peak VRAM, and
power. Treat C16 as beneficial only if it is stable and increases aggregate
throughput materially over C8. A gain below 10%, a sharp MAL collapse, chronic
preemption, or disproportionate p95 latency is diminishing return; in that
case retain `MAX_NUM_SEQS=8` even if a C16 smoke request technically completes.

## Deterministic cold-to-hot CUDA rank binding

CUDA visibility order maps physical GPUs to logical CUDA ordinals and therefore
vLLM TP/DCP ranks. It can change NCCL and SparkInfer/B12X ring/peer adjacency,
communicator ownership, calibration identity, and which physical card carries
rank 0's asymmetric driver, sampler, speculative-decode coordination, and
LMCache-leader work. It does not change model sharding semantics.

Use an explicit bottom-to-top, cold-to-hot order on AIBeast so rank 0 stays on
the coldest card and the physical rank mapping remains deterministic across
boots and driver updates. The Discord workstation's `3,1,2,0` result expresses
the same policy but is machine-specific and must not be copied literally.

AIBeast's repeated observations, including the 2026-08-02 loaded-idle sample,
give this stable cold-to-hot order:

| logical rank | physical GPU | UUID | PCI bus | sample temperature |
|---:|---:|---|---|---:|
| 0 | 2 | `GPU-230586e4-f6e4-08a3-a49b-e9993c746e2c` | `0000:81:00.0` | 31 C |
| 1 | 1 | `GPU-f47ec63c-5d34-d006-b34a-6b9f98c880cf` | `0000:21:00.0` | 32 C |
| 2 | 0 | `GPU-9d6ab48c-556f-ae37-60fe-6d8868c0ce48` | `0000:01:00.0` | 34 C |
| 3 | 3 | `GPU-55e65b01-6535-9fc9-c3f9-74bbc54977d2` | `0000:C1:00.0` | 36 C |

Set the next-window candidate and final AIBeast service to:

```text
CUDA_DEVICE_ORDER=PCI_BUS_ID
CUDA_VISIBLE_DEVICES=2,1,0,3
```

Leave `GPUS` unset so the embedded launcher preserves this intentional CUDA
order. Use a new compile/calibration cache namespace containing `2-1-0-3`, or
verify that the cache fingerprint records the complete ordered UUID/bus list;
never reuse a natural-order PCIe calibration entry under the reordered ranks.

Before stopping the current service, retain its natural-order benchmark and
thermal sample as the control. At the next window, validate the proposed order
during a standardized 128K prefill followed by a long decode, then repeat the
same benchmark after warmup. Record the rank-to-UUID mapping, per-card median
and peak temperature/power, SparkInfer transport selection, PP 3K/32K/128K,
C1/C8 and optional C16 decode, MAL, and collective latency. Performance parity
is sufficient for promotion because deterministic binding, calibration
validity, and keeping rank 0 off the hottest card are the intended benefits;
reject the order only for a repeatable throughput/correctness regression or a
less efficient B12X transport selection. This remains an AIBeast-local setting,
not a provider-wide turnkey default.

## KLD matrix and reporting contract

KLD is a release gate for each distinct **weights + online overlay + KV**
precision combination. MTP depth, concurrency, and GPU ordinal order should
not change target-model prompt logits; do not waste full KLD reloads for every
throughput-only knob. Instead, attach every performance cell to its exact KLD
precision row and run a short invariance/hash check after MTP/order changes.

| row | checkpoint | online overlay | KV | status/purpose |
|---|---|---|---|---|
| K0 | 3.25 bpw | none | dynamic NVFP4/RoPE8 | current control; reproduce the appliance reference if time permits |
| K1 | 3.36 bpw | none | FP8/BF16 RoPE | reproduce the published `0.068458` reference |
| K2 | 3.36 bpw | conservative linear MXFP8 | FP8/BF16 RoPE | reproduce Discord Arm A `0.0686203539` |
| **K3** | **3.36 bpw** | **online Trellis K6 (`exl3-b6`)** | **FP8/BF16 RoPE** | **direct K6-versus-MXFP8 weight-overlay KLD comparison; currently unknown** |
| K4 | 3.36 bpw | none | dynamic NVFP4/RoPE8 | AIBeast/r20 ABI-5 field run: `0.0810645975`, 2,047 positions |
| **K5** | **3.36 bpw** | **conservative linear MXFP8** | **dynamic NVFP4/RoPE8** | **AIBeast/r20 ABI-5 field run: `0.0812378737`, 2,047 positions; model VRAM 83.43 → 80.06 GiB/GPU** |
| **K6** | **3.36 bpw** | **online Trellis K6 (`exl3-b6`)** | **dynamic NVFP4/RoPE8** | **AIBeast/r20 ABI-5: `0.0825070356`, exact repeat; selected production precision** |
| K7 optional | 3.36 bpw | linear + shared-expert MXFP8 | dynamic NVFP4/RoPE8 | run only if K5/K6 fail the capacity goal and the extra memory is needed |

Use the same BF16 reference revision, tokenizer, IndexCache pattern, prompt
positions, KLD direction `KL(BF16 || candidate)`, and evaluator revision for
all rows. Report sample count, evaluated token/position count, mean, sample SD,
minimum, maximum, and raw artifact paths. The standard 2,047-position result
is required for continuity with appliance history. Also reproduce the reported
408,423-token LAVD arm if its exact harness and BF16 reference artifacts are
available; otherwise retain it as upstream evidence and state plainly that it
was not independently reproduced.

Do not mix KLD values across FP8/BF16-RoPE and dynamic-NVFP4/RoPE8 when ranking
the weight overlay. K3 directly tests the claimed K6 quality advantage over
MXFP8; K5 versus K6 decides the production tradeoff under dynamic NVFP4. The
K6 **cache mechanism** affects disk use and startup, while the encoded K6
weights affect VRAM, throughput, and KLD. KLD must be measured from served
logits and cannot be inferred from a successful cache hit or nominal bit width.

## Efficient boot order

1. Capture and benchmark the exact live r17/3.25 production control, then stop
   it cleanly with rollback artifacts preserved.
2. Boot r20/3.36 native at K4 and verify r20 compatibility, block-32 selection,
   memory, KLD, API features, and a short correctness gate. Use
   `expandable_segments:False` whenever LMCache is enabled. Measure
   `VLLM_EXL3_PREFILL_CAPACITY` unset first, then `1024` with every other byte
   of configuration held constant; keep `1024` only if its measured KV gain is
   worth the PP loss for the 524K production envelope.
3. Boot r20/3.36 `exl3-b6` at K6 in an isolated empty persistent cache, then
   warm-restart it from that cache. Record conversion and startup time, cache
   count/bytes/hash/hits, weight VRAM, active KV, PP/TG, and KLD/correctness.
4. Boot r20/3.36 conservative online MXFP8 at K5. Measure final model VRAM,
   auto-profiled blocks, pinned 524K behavior, PP/TG, and full KLD/correctness.
5. Select K6 or K5 only after a matched native/K6/MXFP8 comparison. K6 wins if
   it confirms both lower VRAM and lower KLD without a material PP/TG or
   reliability regression. On the selected boot family, perform the matched
   MTP3/MTP5 C8 comparison.
6. Qualify MTP3/C16; attempt MTP5/C16 only if its 96-row graph/Trellis contract
   is supported and memory-safe.
7. Validate and repeat the AIBeast cold-to-hot `2,1,0,3` rank binding on the
   selected precision/MTP shape, using the captured natural-order production
   result as its control and a mapping-specific compile/calibration cache.
8. Run the matched K1/K2/K3 FP8-KV rows after K5/K6 are safe. They isolate the
   weight-overlay KLD claim; production still uses dynamic NVFP4.
9. Complete 256K and exact near-maximum five-depth needles, degeneration,
   structured output, tool use, LMCache DRAM/NVMe cold/warm/restart, allocator
   fragmentation, and agent soak tests on the final candidate.
10. Restore port 8000 with `GLM-5.2` and `local-primary`; promote the candidate
   only if all release gates pass, otherwise restore the captured r17 control.
